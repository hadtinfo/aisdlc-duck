Claude Code plugin · Go · PostgreSQL

The agent writes the code. You approve each gate.

AISDLC is a quality-gated feature workflow for teams building Go services with Claude Code agents. The agent writes the BRD, design, test cases and code; a developer approves every gate. Plugin hooks stop the agent from taking shortcuts, and CI re-checks every merge request.

How it works

A feature passes through five gates. Each one must be approved before the next opens. Approved artifacts are locked by hash; changing one means the developer reopens its gate.

Approval gates

The agent may only write product code once BRD, Design and Cases are approved. Approved artifacts are locked by hash.

Step-by-step coding

Each step S1…Sn declares a file scope (globs) and a budget (files, lines). Writes outside the scope are blocked unless the developer allows each file.

Cases before code

HTTP, DB, message and stub cases are written and locked first, and must fail at submission. The harness runs them as a black box against the real service, with Postgres (and Kafka) in Docker.

Eval & review

Build, go test, the case suite, coverage of new lines and an independent subagent review, written to eval/report.md. CI re-runs it on the MR.

Who does what

Agent (Claude Code)Developer
Writesbrd.md, design.md, design.yaml, migrations, cases.yaml, codeNothing required: reads the review card, diff and report

Two flows. FULL (default) goes through all five gates and is meant for changes touching the DB, APIs or money movement. LITE (aisdlc init KEY --lite) is for small bug fixes: it skips BRD and Design, leaving Cases → S1 → Review.

Install & attach to a service

You need Linux or macOS, Go, Docker (the harness starts Postgres/Kafka), git and Claude Code.

  1. Install the plugin on your machine

    The script builds aisdlc and aisdlc-harness for your platform and links ~/.local/bin/aisdlc (add it to PATH).

    git clone https://github.com/hadtinfo/aisdlc-duck.git ~/aisdlc
~/aisdlc/plugin/install.sh

    Then, inside Claude Code:

    /plugin marketplace add ~/aisdlc
/plugin install aisdlc@aisdlc

    No Go on the machine? Download the prebuilt plugin bundle from GitHub Releases, extract it and point /plugin marketplace add at the extracted directory.

  2. Attach it to a service repo (in its own MR)

    At the root of a Go service with go.mod, cmd/<name>/main.go and goose migrations:

    aisdlc setup --preset generic     # or --preset banking
git status --short

    This creates aisdlc/config.yaml, aisdlc/risk-policy.yaml, aisdlc/gitlab-ci.aisdlc.yml, adds an AISDLC section to CLAUDE.md and ignores .aisdlc/. Check the service and migrations sections of the config.

  3. Make sure the service meets the harness contract

    • Reads its port and DB URL (and Kafka brokers) from the variables named in service.env.
    • service.healthPath returns 2xx when ready.
    • Exits cleanly on SIGTERM (otherwise new-line coverage is N/A).
    • Goose migrations named NNNNN_name.sql with -- +goose Up.

  4. Build a feature

    /aisdlc:init PAY-123  →  /aisdlc:brd  →  /aisdlc:design  →  /aisdlc:cases
/aisdlc:step S1  …  /aisdlc:step Sn  →  /aisdlc:review

    After each stage, approve in a separate terminal: aisdlc approve design, aisdlc step accept S1… Merge the setup MR first, then enable CI in a later MR.

Walkthrough: PAY-1 “daily limit check”

The same scenario the E2E test runs on the sample service e2e/fixture-service. The repo's risk policy has a rule described as “Chặn giao dịch theo hạn mức” (blocking transactions by a limit) at level high, which requires a duplicate-request case and a DB invariant. (This run uses a Vietnamese repo, so the CLI output is in Vietnamese with translations in the comments; a repo with locale: en prints it in English.)

1 · Initialize and write the BRD

claude code · agent
$ aisdlc init PAY-1 --title "Kiểm tra hạn mức ngày"
Đã tạo tính năng PAY-1 (luồng FULL): Kiểm tra hạn mức ngày
  aisdlc/features/PAY-1/brd.md
  aisdlc/features/PAY-1/design.md
  aisdlc/features/PAY-1/design.yaml
  aisdlc/features/PAY-1/cases.yaml
Tiếp theo: soạn brd.md rồi chạy `aisdlc submit brd`.   # next: write brd.md, then submit

$ aisdlc submit brd
Đã nộp cổng BRD, không có phát hiện.            # BRD submitted, no findings; the dev always approves BRD

2 · The developer approves — in their own terminal

If the agent tries to approve, it is refused (exit 3), and the hook blocks code writes while the gate is closed. The developer reads the review card and retypes the feature key:

developer terminal
$ aisdlc approve brd
Review card — PAY-1 · cổng BRD
Cờ đỏ (2)                                       # red flags
  [WARN] BRD_RULE_NO_ID: 4 quy tắc nghiệp vụ không có ID BR-n …
Gõ lại feature key (PAY-1) để xác nhận: PAY-1
Đã duyệt cổng BRD bởi dev (hash …).             # BRD approved

To send it back instead: aisdlc reject brd -m "Number each rule BR-n" — feedback lands in feedback.md.

3 · Design: steps with scope and budget

steps:
  - id: S1
    title: Kiểm tra request
    scope: ["internal/limit/web/**", "cmd/server/routes.go"]
    budget: { files: 2, lines: 60 }
  - id: S2
    title: Tính hạn mức theo bảng daily_limit
    scope: ["internal/limit/**", "db/migrations/**"]
    budget: { files: 3, lines: 80 }
invariants:
  - name: Số đã dùng không vượt hạn mức
    sql: "SELECT account_id FROM daily_limit WHERE used_amount < 0 OR used_amount > limit_amount"

Before submitting, the agent runs aisdlc risk inputs and hands the listed files to the read-only subagent aisdlc-risk-classifier, which matches each rule by meaning and quotes its evidence (rule E1: “App chặn sớm giao dịch chuyển tiền vượt hạn mức ngày của tài khoản”). submit design checks that result against the current documents, test-runs the draft migration on a real Postgres and records level high. The review card flags SCOPE_OVERLAP (S1 and S2 both touch internal/limit/web/**) and SCOPE_MATCHES_OLD_MIGRATION — see the Design gate screenshot below.

4 · Cases are checked against the risk level

claude code · agent
$ aisdlc submit cases
RISK_REQ: Mức high yêu cầu Case gửi trùng: … POST /api/v1/limits/check
# level high requires a duplicate-request case
(exit 1)

The agent adds case C7 (when.repeat: 2, checks used_amount does not change) and resubmits. Since no code exists yet, some cases fail — which is required. Once approved, cases.yaml is locked; the hook even blocks sed -i on it.

5 · Code step by step, inside the scope

claude code · agent
$ aisdlc step finish S1
2/2 pass                                        # S1 → AWAITING_DEV, agent stops

$ aisdlc step finish S2
Ngoài phạm vi: README2.txt                      # out of scope → exit 1

The developer decides: delete the file, or aisdlc scope allow README2.txt. After a rerun S2 reports 7/7 pass, and the developer runs aisdlc step accept S2.

6 · Eval, independent review, MR

/aisdlc:review runs aisdlc eval (first line of eval/report.md: Eval PAY-1: ĐẠT — PASS), asks the aisdlc-reviewer subagent to score five criteria, then submits. After aisdlc approve review, open the MR: the CI job runs aisdlc eval --ci. If anyone edits cases.yaml after approval, CI fails at CASES_LOCKED.

Web UI (optional)

aisdlc-web adds a feature board, a live view of the agent, approving gates in the browser, pausing the agent, sending instructions, and accepting steps or allowing files. Each user picks English or Vietnamese with the EN/VI switch; the screenshots show the Vietnamese UI.

Run it locally

docker build -f Dockerfile.web -t aisdlc-web .
docker run -d --name aisdlc-db -e POSTGRES_USER=aisdlc -e POSTGRES_PASSWORD=change-me \
  -e POSTGRES_DB=aisdlc postgres:16-alpine
docker run -d --name aisdlc-web -p 127.0.0.1:8080:8080 --link aisdlc-db \
  -e AISDLC_DB_URL=postgres://aisdlc-db:5432/aisdlc -e AISDLC_DB_PASSWORD=change-me \
  -v aisdlc-data:/data aisdlc-web

docker exec aisdlc-web /aisdlc-web user add dev "Dev Name" --email dev@example.com
# sign in with the printed token, create an ingest token on /me, then:
aisdlc web login

Set approvals: web in aisdlc/config.yaml to keep approval records on the server; CI then asks the web instead of trusting the repo. Production setup: web operations.

Risk policy

Each repo declares a level scale, rules written in plain words and requirements per level. An independent subagent classifies each feature once, at the Design gate, quoting the text behind every matched rule; CI re-checks that the result still matches the documents. Low levels can auto-approve clean Design, Cases and step submissions — BRD and Review are always manual.

flow:
  low:    { design: auto,   cases: auto,   step: auto }
  medium: { design: manual, cases: manual, step: auto }
  high:   { design: manual, cases: manual, step: manual }
RequirementMeaning
rule-pos-negEach BR-n rule has a happy case and an error/boundary case
idempotentEach write endpoint has a case with when.repeat ≥ 2
concurrentAt least one case with when.parallel ≥ threads
invariantThe design declares SQL invariants that must return 0 rows
coverageNew-line coverage ≥ min%
sql-zeroA project query must return 0 rows after the last step

Safety model

AISDLC assumes the agent can make mistakes, not that it is deliberately attacking. Hooks catch honest mistakes on the developer's machine; protected branches plus the CI eval job are the real enforcement layer.

PreToolUse hook

Blocks writes to state files and approved artifacts, writes outside the step scope, access to ~/.config/aisdlc, and commands that print environment variables.

No network in hooks

Hooks only read a cache signed with Ed25519 by the server; the public key is pinned on the developer machine.

CI re-checks

CI fails when a gate isn't approved, content doesn't match the approved hash, or code changed after the Review approval.

Blocking writes via Bash is a heuristic. Known bypasses are listed in section 8.1 of the user guide. To report a vulnerability, see SECURITY.md.
